# The Go backend and the live stream

Where Dawnline's backend is going, what is built, and the order of the rest. Read with `rules/backend-go.md` (how the Go code is written) and `rules/frontend.md` › Live data.

## Why

Three things are wrong with the ucode backend, and they have one cause: nothing in it stays running with the state in memory.

- **Every page asks for everything.** The admin fetches `status` (the whole model: every server, person, device, counter and the last 60 events) every 30 s and on each move of a revision it polls every 2 s. The answer is one document, so a page cannot know what changed in it and rebuilds what it shows. One open tab costs a `rev` call every 2 s for nothing.
- **The portal pays 140 ms of CPU per request before any work** (a CGI process compiles the module graph), so it does not follow anything: it loads once and polls only while a set-up sheet is open.
- **State is passed between processes as files** (`presence.json`, `meter.want`, `usage.reset`, …), each with its own lock, format and staleness rule.

The target is what podkop-exp did to podkop's shell backend, for the same reasons: **one long-running Go program** that holds the state, with packages that each have one job, and the pages following it over **a stream of changes** instead of asking again.

## Target

```
                    ┌──────────────────────────── dawnlined (Go, procd) ────────────────────────────┐
 LuCI admin ── uhttpd /ubus ── rpcd ACL ── ubus ──┤ api ──┐                                          │
   (shared/live)   calls + event stream           │       ├── hub ◄── producers: watch, usage, log,  │
 portal ───────── HTTPS (own listener) ───────────┤ portal┘     ▲      people, servers, health, …    │
   (shared/live)   calls + event stream           │             │                                    │
 dawnline CLI ──── unix socket ───────────────────┤ ctl         └── model ◄── uci (/etc/config/dawnline)
                                                  │                  apply ──► awg, nft, netifd, fw  │
                                                  └──────────────────────────────────────────────────┘
```

- **`hub`** holds the live state as named documents (*topics*) and publishes each change as a numbered event. It knows no transport and owns no data.
- **Producers** own the data: one goroutine each, or one supervisor loop for everything that changes the router (one writer per resource, as today, without lock files).
- **`api`** (admin, over ubus) and **`portal`** (people, over its own HTTPS listener) are doors onto the hub plus the commands. The admin stays a LuCI page: its login, sessions and access lists are rpcd's.
- The settings stay `/etc/config/dawnline` in today's format. Nothing a user has changes with the backend's language.

## The stream

The same protocol over both doors; `web/src/shared/live` is its client.

**Topics.** A topic is a JSON document: `people`, `servers`, `traffic`, `meter`, … A list of things that have an id is published as a *keyed list*, `{ "order": [ids], "items": { id: {…} } }`, so one entry changing does not resend the list. A daily series is keyed by its `day` the same way: on a real router the arrays of days were most of what a minute's refresh resent.

**Events.** Every change of every topic is one event, numbered from 1 in the order it happened: `{ seq, topic, op, data }`.

| `op` | `data` | |
|---|---|---|
| `put` | the document | first time, or it is not an object |
| `patch` | a JSON Merge Patch (RFC 7396) | only the fields that changed; `null` removes one. Documents hold no `null` |
| `append` | `{ items, keep }` | new entries of a list (a log, the meter's points); the list holds its newest `keep` |
| `drop` | — | the topic is gone |

A producer puts a whole document as often as it likes; the hub works out the patch and publishes nothing when nothing changed. Producers never write patches by hand.

**Following.** A page takes a snapshot once (`sync` with no position → `{ epoch, seq, docs }`), then applies events in order. The next event is always `seq + 1`. Anything else (a number skipped, another `epoch`: the backend restarted) means *ask where we are*: `sync { epoch, seq }` answers with the events missed (the last 512 are kept) or a new snapshot. A page is therefore never wrong for longer than it takes to notice, and never needs "refresh everything" logic of its own.

**Two transports, same events, same numbers:**

- **Event stream** (SSE): `GET /ubus/subscribe/dawnline` with the session as a Bearer token. uhttpd turns the object's ubus notifications (`event`, and `ping` every 15 s of silence, carrying the current `seq`) into `text/event-stream`. Used where uhttpd can hold one.
- **Held call** (long poll): `wait { epoch, seq, timeout }` answers when there is an event. Works through any web server LuCI runs on.

`hello` says which to use. **uhttpd before 2026-08-03 leaks every subscription's connection** (fixed upstream in `3c48b9e`; the 24.10.6 and 25.12.3 images ship a uhttpd from before it, 25.12.5 one from after) and stops serving once `max_connections` of them are open, so the stream is used only where the installed uhttpd has the fix; a page also gives a stream up for the held call after it fails twice. Today the choice is `dawnlined -stream sse|poll` and defaults to `poll`; stage 2 has the init script set it from the installed uhttpd's version. Not WebSocket: uhttpd has none, and nothing here is said from the page to the router that a plain call does not say better.

**Only while someone looks.** Each question renews a 30 s lease on the topics it names; subscribers count too. Producers that cost something (the 1-second meter) run only for topics under a lease (`watch { topics }`, renewed by the page every 10 s). No page open: nothing is read for the pages at all. **The meter is the exception since 2026-11-12:** its points cost nothing more to make (the watcher looks at the tunnels every second whoever is there), so the `meter` topic is kept current always and a page has the last two minutes in the answer that starts its look; only the old `meter.json` file is still written under a lease.

**Commands** (creating a device, changing a setting) are calls that answer with their result and the `seq` their change is visible at. The page does not refetch after a command: the change arrives on the stream like anyone else's.

### On the page

- `signal.ts`: signals (`signal`, `computed`, `effect`, `batch`). A text node, an attribute or a list reads the signals it shows inside an effect; only that effect runs when one moves.
- `store.ts`: the topics' documents. `store.at('people', 'items', id, 'online')` is a signal for that one place. Patches are applied with structural sharing, so a part that did not change is the same object and its readers are not told.
- `follow.ts`: the rules above over a `Transport`; pauses while the page is hidden, catches up when it is shown.

This is what replaces "fetch `status`, rebuild the box": a person's card binds its name, its state and each device's `online` to their places, and a device connecting changes one dot.

### Loading: pending, ready, stale

Every topic has a state the page can read (`store.state(topic)`), and that is the whole model for what a page shows before and without data:

| state | means | the page shows |
|---|---|---|
| `pending` | nothing came yet | the page waits under its section row, then comes in whole; not "empty" and not a spinner over the whole page |
| `ready` | the router's document, followed live | the data |
| `stale` | the last document seen, and the stream is down | the data, marked as old; **never** hidden behind a wait the page does not need |

With it the admin's `load()` no longer waits for `status` under LuCI's spinner: the section row stands at once and the page comes in when its answer has come, its blocks rising as the portal's do (`DESIGN.md` › Motion › 16, `rules/frontend.md`). The admin had skeletons (skullet) for a day, 2026-11-12; the owner had them taken out the same day in favour of that entrance. A backend that was just started used to tell its first topics only with the bridge's next Refresh (measured after a deploy, 2026-11-12: every question answered by 2.6 s, the stream's first events at 22 s); that is fixed in the bridge (*Told as the router is at that moment*, below: about 1 s now). The page keeps its own guard all the same: while it waits for its first status it asks for the snapshot itself every 700 ms (`state/stream.ts streamStatus`: `refresh` + `sync`) and takes whichever comes first. The portal's first paint can go further: the backend can put the person's state into the HTML it serves, so there is nothing to wait for (stage 3).

No marker is read any more: where `dawnlined` runs on the router, the init script starts it with its watcher and the portal, and its apply, sync, keeper, chores and watchdog are in charge. Who this leaves out, knowingly: a router whose architecture has no binary (ARM older than v7, 32-bit x86, RISC-V) and a router installed with no network until its first start with one.

**Before any of the ucode can be deleted, a release has to put `dawnlined` on the router.** The package is `all`-architecture and the binary was built by `scripts/deploy.sh` for the development router alone: a router that installs a release gets no backend, and runs entirely on the ucode fallback.

What is in place for it, whichever way the binary is delivered: the release workflow builds it for five architectures (`backend` job in `.github/workflows/build.yml`: arm64, arm for ARMv7, mips, mipsle, amd64; static, 9 to 11 MB each: more than some routers have free, which the install has to check) and publishes each as `dawnlined-<version>-<goarch>` with its sha256 in `sha256sums.txt`; `updater.GoArch` names the one for a router by its `DISTRIB_ARCH` (none for ARM older than v7, x86 32-bit and RISC-V: those stay on the fallback).

How it gets from the release onto the router: **fetched beside the package** (`/usr/libexec/dawnline/fetch-backend`, a plain shell like `postupdate`, since it runs when no backend does). It asks GitHub's API for the release of the installed version, takes the file for this router's architecture through the API (the same way round uclient-fetch's header limit as the updater's), keeps it only when it matches the sha256 the API gives and runs here as that version, and renames it into place. A binary of another version is always removed, fetched or not: two versions never run side by side, and the service then runs on the ucode backend. It is called by `install.sh` after the package is in, by `postupdate` before a new version starts (and again after a rollback), and by the init script in the background, once a boot, when there is no binary. The package's `prerm` removes the file: the package manager does not own it. Tried against a made-up GitHub in both OpenWrt rootfs images: a fresh router, again, over another version, a file that does not match its sha256, a version with no release, an architecture with none.

This was built without the owner's answer to "per-architecture packages or a fetch beside the package", on the recommendation given; it adds a script and three calls and changes no package. Should the answer be per-architecture packages, `fetch-backend` and its calls go, and the release's binaries become those packages' payload.

What it does not give: an install with no network leaves a router without the backend until its next start with one; ARM older than v7, 32-bit x86 and RISC-V have no binary at all. So the ucode fallback cannot be deleted outright yet: it can go once the owner accepts that those routers are no longer served, or the backend is built for them.

### The watcher's takeover (stage 4)

The agent's 1-second watcher and its counters are the Go backend's while its watcher runs; the agent keeps its minute tick. Who owns what:

| | Go backend (`backend/watch`) | ucode agent (until stage 5) |
|---|---|---|
| Every second | the tunnels' dump; presence, link, meter; a connect, a leave, a move, a link's trouble into the activity log; `backend.beat` | looks at the beat's age, and at `geo.poke` |
| Counters | `usage`: folded on every event and every minute, written to tmpfs, to flash hourly and on stop; `usage.reset` and `usage.reload` honoured | reads `usage.json` at each tick, never writes it |
| Files the ucode that remains still reads | `presence.json` (with its revisions), `link.json`, `setup.json`, `usage.json`, `meter.json` while asked, `events.json` under the `events` lock | `rate.json`, `rate_people.json`, the rest of the tick's |
| Revisions | moves them with each event, and for the people named in `presence.poke` | writes `presence.poke` where it used to save presence (a state that moved on its own, a place that was found) |
| Places | a connect's place from the cache when it is known; the addresses that connected or moved into `geo.poke` | the lookups: at once for `geo.poke`, each minute for what is shown (`geo.json`; the bridge watches it and `events.json`) |

Handing over, both ways, is by the beat alone:

- **The backend starts**: it reads `presence.json` (who was online, the revisions) and `usage.json` as the agent left them, so nobody connects or leaves "again" and no counter is lost. What a link showed starts empty: a state shows again once it held.
- **The backend stops** (or a package without it is installed): it folds the counters once more, writes them to flash and removes the beat; the agent's watcher reads the files back within a second and goes on. If it is killed, the beat goes stale in five seconds and the same happens, with at most a minute of traffic counted from the tunnel's own counters at the next look.

Measured on the development router (MT7981, 2026-11-11): the takeover and the take-back moved no revision and logged no event; the counters file after the first Go write had the same devices, people and fields, with only that minute's traffic added; `dawnlined` with the watcher holds about 6 MB.

```
  hub/      topics, merge-patch diff, the numbered journal, wait and follow
  api/      the object `dawnline`: hello, sync, wait, watch; the broadcast; who looks
  bridge/   `status` cut into topics; asks luci.dawnline only while a page looks
  daemon/   the parts joined
  cmd/dawnlined/
web/src/shared/live/   signal.ts, patch.ts, store.ts, follow.ts
scripts/backend-container.sh
```

Verified by `scripts/backend-container.sh` on the OpenWrt 24.10 and 25.12 rootfs images, against their real `ubusd`, `rpcd` and `uhttpd`:

- the object, its signature, calls, statuses and notifications, with OpenWrt's own `ubus` tool on the other side;
- a page's whole path: an rpcd session, the package's ACL file, `sync`, a held `wait`, the event stream, the meter under a lease, arguments refused at the door;
- one device coming online reaches the page as a 67-byte patch about 0.6 s after the agent's file moved (the bridge looks once a second; a native producer in stage 4 publishes at once).

Run on the reference router (2026-11-11, OpenWrt 25.12.5, uhttpd 2026.08.24, from `/tmp` beside the real agent, three people and one server):

- the event stream through that uhttpd holds for 50 s with a ping every 15 s of silence, and its connection is gone when the client leaves (the leak of older builds is not there);
- the snapshot is 40 KB in ten topics, where one `status` answer is 48 KB and takes 0.39 s in rpcd;
- a page that follows receives about 240 bytes per 30 s while nothing happens, and about 13.5 KB when the agent's minute tick moves the counters: `places` 8.7 KB (its points are a list without ids, resent whole) and `people` 2.9 KB are what is left to cut, by the producers of stage 4 rather than in the bridge;
- the daemon holds 9.2 MB of memory and used 0.23 s of CPU in 154 s of being followed.

As a service on that router (the same day, deployed with `scripts/deploy.sh`), with Overview open in a browser: the page asks no `rev` and no `status` at all; the bridge asks the ucode backend for one `status` per 30 s for every open tab together (and at once on a change), and for the meter once a second only while a speed is on screen. The backend holds 4 MB of memory there.

A session opened before the backend's object was in the access list does not have it until its next login (rpcd grants a session its access when it logs in): such a page falls back to asking the router, as on a router without the backend.

## Decisions

- **As little ucode as can be** (the owner, 2026-11-12: «Нужно будет максимально уйти от ucode»). The bridge is scaffolding, not a design: a part is ported, held to ucode on fixtures, compared with it on the real router (`roster`), then published by Go, and its ucode call goes. Nothing stays on the bridge once it is ported.

- **Go, not Rust.** Cross-compiles to every OpenWrt architecture with no SDK, the reference (podkop-exp) proves the approach on the same routers, and nothing here needs what Rust would buy. The cost is the binary: stage 1 is 3.4 MB for aarch64 (3.9 MB mipsle; 1.4 MB gzipped) and 9 MB of memory on the router, and both grow with what is ported.
- **No dependencies so far.** ubus, the hub and the API are the standard library only. A dependency is added when it replaces real work (nftables and netlink in stage 5), not for convenience.
- **podkop-exp is studied, not copied.** Its backend is GPL-2.0-or-later and Dawnline is MIT: its patterns are reused (one door per external system, a single loop for router changes, fakes behind interfaces, golden files from the old backend), its code is not. `backend/ubus` is written from ubus's own protocol (`ubusmsg.h`) and, unlike podkop-exp's, also notifies, calls and reconnects.
- **The package stops being `all`.** A Go binary is per architecture. Until stage 2 ships, the binary is built and deployed for the development router only; the release build then follows podkop-exp's matrix (one SDK image per package architecture) and `install.sh` picks the asset by `DISTRIB_ARCH`.
- **The router's time zone is read from `/etc/TZ`** (`backend/zone`). Go looks for the zone in `TZ` or `/etc/localtime`; an OpenWrt service has neither, so a Go program there counts its days in UTC. Found the first night the watcher ran (2026-11-12, MSK): after local midnight the traffic went on into yesterday's UTC day and «Today» read 0 B. Everything that needs local time asks `zone.Local()`; the watcher takes the file again when it changes. A golden made with `TZ=UTC` cannot see this: `usage` and `zone` have their own tests in a zone east of Greenwich.
- **A router stands for the networks behind it** (site to site, issue 4; 2026-11-12). A device of kind `router` may have networks of its own behind it (`list behind_net`), which the tunnel then carries both ways. `model/behind.go` is the one place that says what may be one (a private network from /16 to /30, eight a router) and which are in effect (`BehindOf`: none that shares addresses with a tunnel's subnet, with a network the router has itself, or with one an earlier device has), so a bad line in the file never takes a route away from the router or from another site. Everything else is made from that answer: the peer's `AllowedIPs` (`apply.PeersConf`); the router's routes (`apply/routes.go`: reconciled, every route of ours marked with routing protocol 205, and only into a tunnel that took its devices); the home-like path (the networks keep their direct route, and the netns answers them through the tunnel); the access sets, where a network stands wherever its router's address does, so a host there has exactly its owner's access and is reached by exactly those who reach the router (every run-time set takes intervals for it: the set declarations in the goldens of `nft` and `apply` were edited by hand, the rest of each table is still ucode's byte for byte); and the configurations of the devices that reach it (`model.BehindReach`), whose fingerprint then tells them to import again. `device_networks` sets a router's networks and ends in the full apply, since the home-like path's rules move. None of this is held to ucode: there never was a ucode version. Checked on real `nft` (1.1.1 and 1.1.6, the table loaded and its sets replaced) and `ip` of OpenWrt 24.10. **On the development router** (2026-11-12, OpenWrt 25.12.5, `nft` 1.1.6, iproute2 6.18, one server with six real devices; a person with the internet alone made for it and removed after, so no real device's configuration was touched): the table with its interval sets loaded on the router's own kernel, `fib` rules and all, with the same members as before; a router added with two networks got them in its peer's AllowedIPs, a route each (`ip route get` answers the tunnel), and its place in `inet_ok` and in no home set; changing the list moved the routes and the same list applied nothing; the refusals named the real tunnel's network and the router's own LAN; a router asked for through the person's link waited outside the tunnel with no configuration (409), was turned down, put back and taken, a network asked for later was taken on its own and another taken away by its owner at once; Health said how many networks the tunnel carries and Check access walked a host behind the router. With the person removed the routes, the peers and the sets were as before and the settings file byte for byte what it was. **Not checked there:** packets through a real far router (no second site to test with), and the home-access case, where other people's devices are given the networks.
- **A router and its networks may be asked of the admin** (2026-11-12). On their own page a person adds a router and names the networks behind it; what then happens is the server's rule (`portal_routers`: off, ask, free; `portal_nets`: ask, free; a server starts with ask for both, and the page is told the rule and is not offered a router where it is off). Asked, neither takes effect: the router waits (`waiting`: no device of the tunnel, in no access set, no configuration, no new keys; `health.TunnelDevices`, `nft.AccessSets`, `model.BehindOf` and the methods that hand a configuration out each leave it out) and the networks are only asked for (`ask_net`, `asked`). `device_answer` is the admin's answer: accept (checked now against everything the networks must not share addresses with, refused in a sentence that names whose they are), decline with a reason the person reads (`declined`: one of four words the pages put in their reader's language; `declined_net` for networks; a router turned down stays, waiting, for its owner to read why and remove), or reopen, the undo of either. Taking a network away is the person's own to do, at once (`DeviceWishAs`, the portal's `networks` action). A person is never told whose a network is unless it is their own: while something is only asked, other people's networks are not held against it at all, and the admin's answer is where the clash is said. What moved decides how it is put into effect: the routes (the full apply), who is in a tunnel (the sync), or nothing on the router. The model's goldens gained the two rules on every server by hand.
- **Check access and Health know the networks behind routers** (2026-11-12). An address typed into «Check access» that stands in such a network is a host behind its router: the walk says so first («192.168.2.10 is behind Boris · Dacha») and then goes on as it does for the router itself, since the access table sees the two alike; the router and what is behind it, or two hosts behind one router, need no tunnel between them, and that is the answer. A router that waits for the admin stands for nothing. Health has one more check a server (`sites_<id>`, on the page's Home stage), only where a router has a network written: every network in effect, or which is not and what it shares addresses with (a tunnel, the router's own network, another router's), or the route the last sync could not set (`routes.err`), with the sync as its fix. The household's 580 connections held to ucode come out as before.
- **ucode output is the oracle.** When a part is ported, its Go version is held to the ucode one's answers on the same input (fixtures from `tests/ucode`), as podkop-exp holds its planner to the shell backend's configurations.
